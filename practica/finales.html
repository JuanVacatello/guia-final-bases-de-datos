3a · Tipo A · Script sobre TABLITAFINAL(numero UNIQUE)

Tabla vacía, sin triggers. Indicar errores y contenido final:

INSERT INTO tablitafinal VALUES (1);
INSERT INTO tablitafinal VALUES (3);
INSERT INTO tablitafinal VALUES (NULL);
UPDATE tablitafinal SET numero = ISNULL(numero, 5) + 1
 WHERE 1 = 1 OR numero IS NOT NULL AND numero > 0;
INSERT INTO tablitafinal VALUES (NULL);
COMMIT;
Ver la solución

Contenido final: NULL, 2, 4, 6. Único error: el COMMIT (no hay BEGIN TRANSACTION abierto; cada sentencia ya se confirmó sola).

AND se evalúa antes que OR: 1=1 OR (…) es siempre verdadero y el UPDATE toca las 3 filas: 1→2, 3→4, NULL→ISNULL(NULL, 5) + 1 = 6. Como ya no queda ningún NULL, el último INSERT NULL entra (UNIQUE admite uno).

3b · Tipo D · SERIALIZABLE y UPDATE sobre «product»

Igual al del 10/03/2021: A y B en SERIALIZABLE con bloqueo de tabla compartido; los dos leen el detalle del producto 1 y después hacen UPDATE product SET detalle = 'X' (o 'Y'). Opciones: deadlock, queda X, queda Y, termina primero A o B, ninguna.

Ver la solución

Ninguna de las anteriores, siguiendo la clave oficial del mismo ejercicio en 2021. La tabla se llama producto y el UPDATE apunta a product: falla en los dos procesos, no hay deadlock y el detalle no cambia.

⚠️ El alumno de 2023 respondió «deadlock» (sin nota visible). Si la tabla estuviera bien escrita, sí sería deadlock. Leé los nombres letra por letra.

3a · Tipo D · El SP descuenta_stock 
CREATE PROCEDURE descuenta_stock (@prod_id INT, @id_dep INT, @cant INT)
AS
BEGIN TRANSACTION
  IF EXISTS (SELECT 1 FROM stock WHERE id_producto = @prod_id
              AND id_deposito = @id_dep AND cantidad >= @cant)
  BEGIN
    UPDATE stock SET cantidad = cantidad - @cant
     WHERE id_producto = @prod_id AND id_deposito = @id_dep
    COMMIT
  END
  ELSE
    ROLLBACK

El nivel de aislamiento se define en cada ejecución. 1) siempre funciona bien; 2) puede dejar stock negativo; 3) con algún nivel puede dar interbloqueo; 4) todas.

Ver la solución

2 y 3. Con READ COMMITTED el SELECT del IF suelta el bloqueo apenas lee: dos ejecuciones validan el mismo stock y las dos descuentan (negativo). Con REPEATABLE READ o SERIALIZABLE las dos retienen su bloqueo compartido y después piden exclusivo: deadlock.

Corrección: validar y descontar en el mismo UPDATE (AND cantidad >= @cant) y mirar @@ROWCOUNT. Está en las plantillas.

3b · Tipo C · No puede haber dos veces el mismo depósito para el mismo producto (los datos NO están bien)
Ver la solución

Como los datos ya tienen duplicados, una UNIQUE no se puede crear directamente. Dos pasos:

  1. Consolidar en una transacción: sumar las cantidades de cada par repetido, borrar las filas repetidas e insertar una por par.
  2. Impedir que vuelva a pasar: ALTER TABLE Stock ADD CONSTRAINT uq_stock UNIQUE (id_producto, id_deposito) (o un trigger AFTER INSERT, UPDATE con GROUP BY … HAVING COUNT(*) > 1).
-- Motor: SQL Server (T-SQL)
CREATE PROCEDURE sp_consolidar_stock
AS
BEGIN
  SET NOCOUNT ON;
  BEGIN TRY
    BEGIN TRANSACTION;
    SELECT id_producto, id_deposito, SUM(cantidad) AS cantidad
      INTO #consolidado
      FROM Stock WITH (TABLOCKX)
     GROUP BY id_producto, id_deposito
    HAVING COUNT(*) > 1;

    DELETE s
      FROM Stock s
      JOIN #consolidado c ON c.id_producto = s.id_producto
                         AND c.id_deposito = s.id_deposito;

    INSERT INTO Stock (id_producto, id_deposito, cantidad)
    SELECT id_producto, id_deposito, cantidad FROM #consolidado;
    COMMIT TRANSACTION;
  END TRY
  BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
    THROW;
  END CATCH
END;
GO
EXEC sp_consolidar_stock;
ALTER TABLE Stock ADD CONSTRAINT uq_stock_producto_deposito UNIQUE (id_producto, id_deposito);

3a · Tipo A · TOP 5 menores y mayores con un valor duplicado

Secuencias: al menos 20 filas, clave sin nulos y con un solo valor duplicado. ¿Da error? Si no, ¿cuántas filas como mínimo y como máximo?

SELECT clave FROM Secuencias
 WHERE clave IN (SELECT TOP 5 clave FROM Secuencias ORDER BY clave)
    OR clave IN (SELECT TOP 5 clave FROM Secuencias ORDER BY clave DESC)
 ORDER BY 1
Ver la solución

No da error. Mínimo 10, máximo 11. Cada TOP 5 trae 5 claves y el IN compara contra la tabla entera: si el valor duplicado es uno de esos 10, entran sus dos copias (11 filas). Si no, 10. Con 20 filas o más, los dos TOP 5 no se pisan.

3b · Tipo B · Borrar los 2 registros duplicados con una sola sentencia DML
Ver la solución 
DELETE FROM Secuencias
 WHERE clave IN (SELECT clave FROM Secuencias GROUP BY clave HAVING COUNT(*) > 1);

Borra las dos copias (el enunciado pide «los 2 registros»).

3.1 · Tipo A/B · T1 −< T2 >− T3 (T2 es la tabla intermedia, PK (t1_id, t3_id)) 
SELECT T1.id,
       (SELECT COUNT(DISTINCT T2.t3_id) FROM T2 WHERE T2.t1_id = T1.id)
  FROM T1

a) ¿Qué devuelve? b) Reescribila sin subconsultas. c) ¿Qué cambia si se saca el DISTINCT?

Ver la solución

a) Cada id de T1 con la cantidad de T3 distintos relacionados (0 si no tiene ninguno).

-- b)
SELECT T1.id, COUNT(T2.t3_id)
  FROM T1
  LEFT JOIN T2 ON T2.t1_id = T1.id
 GROUP BY T1.id;

b) LEFT JOIN para no perder los T1 sin relación, y COUNT(T2.t3_id) (no COUNT(*)) para que cuenten 0. c) Nada: (t1_id, t3_id) es la PK de T2, no puede haber repetidos.

Ver la solución

3a · Tipo B · Primer hueco de clave en Numeros(clave PK, valor)

clave > 0 garantizado y la tabla no está vacía. Consulta ANSI que devuelva el primer número libre, o el siguiente al máximo si no hay huecos.

Ver la solución 
SELECT CASE
         WHEN NOT EXISTS (SELECT 1 FROM Numeros WHERE clave = 1) THEN 1
         ELSE (SELECT MIN(n.clave) + 1
                 FROM Numeros n
                WHERE NOT EXISTS (SELECT 1 FROM Numeros m WHERE m.clave = n.clave + 1))
       END AS primer_libre;

La clave cuyo siguiente no existe marca el comienzo de un hueco; la menor de ellas + 1 es el primero libre. Si no hay huecos, esa clave es el máximo. El caso que fallaba en las resoluciones de alumnos: que falte el 1.

3b · Tipo B · Insertar un registro con esa clave y valor NULL. ¿Puede fallar?
Ver la solución 
INSERT INTO Numeros (clave, valor)
SELECT CASE
         WHEN NOT EXISTS (SELECT 1 FROM Numeros WHERE clave = 1) THEN 1
         ELSE (SELECT MIN(n.clave) + 1 FROM Numeros n
                WHERE NOT EXISTS (SELECT 1 FROM Numeros m WHERE m.clave = n.clave + 1))
       END,
       NULL;

Sí puede fallar: dos ejecuciones concurrentes calculan el mismo hueco y la segunda viola la PK.

3a · Tipo D · sp_increment_parametro con muchos usuarios en SERIALIZABLE

PARAMETROS(clave PK, valor VARCHAR NULL). El SP hace: BEGIN TRAN; SELECT @valor = valor …; UPDATE … SET valor = @valor + 1; COMMIT.

Ver la solución

Deadlocks: todos leen la misma fila con bloqueo compartido retenido (SERIALIZABLE) y después piden exclusivo. El motor elige víctimas; esas invocaciones terminan con error y su incremento se pierde. Además, valor es VARCHAR: @valor + 1 fuerza una conversión a número que falla si el valor no es numérico (y si es NULL, queda NULL).

Arreglo: UPDATE Parametros SET valor = CAST(valor AS INT) + 1 WHERE clave = @clave, una sola sentencia.

Ver la solución

La segunda clave más chica y la segunda más grande. f1 nunca puede ser el mínimo (tiene que ser mayor que algún f2) y f2 nunca puede ser el máximo.

3a · Tipo A · Juego de cartas: qué devuelve una consulta con CASE y TOP 1

Juego(jugador, jugada, carta), 2 jugadores; gana la carta mayor y en empate gana el 1; empieza el 1 y después el ganador de la mano anterior. La consulta ordena por jugada y por un CASE con SELECT TOP 1 … ORDER BY carta DESC de la jugada anterior.

Ver la solución

Devuelve las jugadas en orden y, dentro de cada una, primero al que ganó la mano anterior. Falla en los empates: el TOP 1 … ORDER BY carta DESC entre dos cartas iguales puede devolver cualquiera de los dos jugadores; no garantiza al 1. Habría que ordenar por carta DESC, jugador.

3b · Tipo B · Mayor carta de cada jugador; primero el de la mayor (empate: jugador 1). Sin subconsultas en el FROM, cursores ni vistas
Ver la solución 
SELECT jugador, MAX(carta) AS mayor_carta
  FROM Juego
 GROUP BY jugador
 ORDER BY MAX(carta) DESC, jugador;

3a · Tipo C · Claves consecutivas desde 1 (ya hay un INSTEAD OF que no se puede tocar)
Ver la solución 
-- Motor: SQL Server (T-SQL)
CREATE TRIGGER tr_numeros_consecutivos ON Numeros
AFTER INSERT
AS
BEGIN
  SET NOCOUNT ON;
  IF (SELECT MAX(clave) FROM Numeros) <> (SELECT COUNT(*) FROM Numeros)
  BEGIN
    ROLLBACK TRANSACTION;
    THROW 50004, 'Las claves tienen que ser consecutivas desde 1.', 1;
  END
END;

AFTER porque no puede haber dos INSTEAD OF INSERT. Con claves positivas (constraint) y únicas (PK), «MAX = COUNT» equivale a «1..n sin huecos».

3b · Tipo C · Valores no nulos de valor únicos. ¿Por qué no con UNIQUE?
Ver la solución 
-- Motor: SQL Server (T-SQL)
CREATE TRIGGER tr_numeros_valor_unico ON Numeros
AFTER INSERT, UPDATE
AS
BEGIN
  SET NOCOUNT ON;
  IF EXISTS (SELECT valor FROM Numeros
              WHERE valor IS NOT NULL
              GROUP BY valor
             HAVING COUNT(*) > 1)
  BEGIN
    ROLLBACK TRANSACTION;
    THROW 50005, 'Los valores no nulos no se pueden repetir.', 1;
  END
END;

UNIQUE no sirve porque en SQL Server admite un solo NULL, y la regla permite muchos.

3a y 3b · Tipo A · Alojamientos y feriados de 2012 con RIGHT y LEFT JOIN

N = cantidad de feriados de 2012.

-- 3a
SELECT COUNT(*), FechaCheckOut
  FROM Alojamientos RIGHT JOIN Feriados ON FechaCheckOut = Fecha AND anio = 2012
 GROUP BY FechaCheckOut ORDER BY 2;
-- 3b
SELECT COUNT(*), Fecha
  FROM Alojamientos LEFT JOIN Feriados ON FechaCheckOut = Fecha AND anio = 2012
 GROUP BY Fecha ORDER BY 2;
Ver la solución

Las dos: como máximo N + 1 filas. 3a: hasta N fechas de checkout que coinciden con un feriado de 2012, más un grupo NULL con todos los feriados sin checkout (incluidos los de otros años, que el RIGHT JOIN conserva). 3b: hasta N fechas de feriado más un grupo NULL con los alojamientos que no salieron un feriado.

⚠️ La resolución del alumno dice «máximo N»: se olvida del grupo NULL.

3a · Tipo B · Por usuario: nombre, alta, estado, cantidad de perfiles, perfil con más logins fallidos y fallidos totales (sin subselects en el FROM)

SELECT u.usua_nombre, u.usua_fecha_alta, e.esta_detalle,
       COUNT(up.perf_id) AS cantidad_perfiles,

3b · Tipo C · Que nadie termine siendo ancestro de sí mismo
Ver la solución 
-- Motor: SQL Server (T-SQL)
CREATE TRIGGER tr_persona_sin_ciclos ON Persona
AFTER INSERT, UPDATE
AS
BEGIN
  SET NOCOUNT ON;
  DECLARE @ciclos INT;

  WITH ancestros (origen, id, nivel) AS (
    SELECT i.id, i.su_padre_es, 1
      FROM inserted i
     WHERE i.su_padre_es IS NOT NULL
    UNION ALL
    SELECT a.origen, p.su_padre_es, a.nivel + 1
      FROM ancestros a
      JOIN Persona p ON p.id = a.id
     WHERE p.su_padre_es IS NOT NULL
       AND a.id <> a.origen     -- si ya volvió al origen, no sigue
       AND a.nivel < 1000       -- tope de seguridad
  )
  SELECT @ciclos = COUNT(*)
    FROM ancestros
   WHERE id = origen
  OPTION (MAXRECURSION 0);

  IF @ciclos > 0
  BEGIN
    ROLLBACK TRANSACTION;
    THROW 50007, 'Una persona no puede ser ancestro de sí misma.', 1;
  END
END;

Desde cada fila nueva o modificada se sube por su_padre_es; si algún ancestro es la misma persona, hay un ciclo. Hace falta recursión porque la profundidad es desconocida. El CTE no puede ir dentro de un IF: se guarda el resultado en una variable.

3a · Tipo B · Los países que no tienen ciudades cargadas
Ver la solución 
SELECT p.idpais, p.detalle
  FROM Pais p
 WHERE NOT EXISTS (SELECT 1
                     FROM Provincia pr
                     JOIN Ciudad c ON c.idpcia = pr.idpcia
                    WHERE pr.idpais = p.idpais);
