SQL: joins, NULL y plan de ejecución

Lo que necesitás para los dos prácticos más frecuentes: «¿qué devuelve esta consulta?» (tipo A) y «escribí la consulta» (tipo B). En teoría salen los tipos de join y el plan de ejecución.

🟦 En 30 segundos

  • JOIN: INNER (solo las que coinciden), LEFT/RIGHT (todas las de un lado + NULL), FULL (todas de los dos lados), CROSS (producto cartesiano: todas con todas). Cartesiano con una tabla vacía = vacío.
  • NULL no es igual a nada, ni a otro NULL: = NULL nunca da verdadero (se usa IS NULL). COUNT(col), SUM, MAX ignoran los NULL; COUNT(*) cuenta filas.
  • Precedencia: NOT, después AND, después OR. 1=1 OR a AND b es siempre verdadero. Y un JOIN o WHERE sobre la tabla de la derecha anula un LEFT JOIN.
  • El plan de ejecución muestra cómo el motor resuelve la consulta (scan o seek, tipo de join, costos): sirve para encontrar el cuello de botella y decidir índices.

    🟪 Respuestas modelo

    Desarrolle el concepto de join, enumere y explique los tipos, con ejemplos 3 veces

    Un join combina filas de dos tablas en una sola fila de resultado según una condición, normalmente la igualdad entre una FK y una PK. En álgebra relacional es un producto cartesiano seguido de una selección. Con Empleado(nombre, depto) y Depto(id, nombre):

    • INNER JOIN: solo las combinaciones que cumplen la condición. Empleado e JOIN Depto d ON e.depto = d.id: los empleados que tienen departamento.
    • LEFT (OUTER) JOIN: todas las filas de la izquierda; si no hay pareja, las columnas de la derecha quedan en NULL. Todos los empleados, con o sin departamento.
    • RIGHT (OUTER) JOIN: lo mismo con la tabla de la derecha: todos los departamentos, aunque no tengan empleados.
    • FULL (OUTER) JOIN: todas las filas de las dos tablas, emparejadas cuando se puede.
    • CROSS JOIN: producto cartesiano, todas con todas (n × m filas); si una tabla está vacía, el resultado es vacío.
    • Self-join: una tabla consigo misma con dos alias. Persona h JOIN Persona p ON h.su_padre_es = p.id: cada persona con su padre.

    Explique la utilidad de obtener el plan de ejecución de un SELECT 2 veces

    El plan de ejecución es la secuencia de operaciones que el optimizador eligió para resolver una consulta: en qué orden accede a las tablas, si usa un índice (seek) o recorre toda la tabla (scan), qué algoritmo de join aplica (nested loops, hash, merge), si ordena, y el costo estimado y la cantidad de filas de cada paso. En SQL Server se ve con Ctrl+L (estimado), Ctrl+M (real) o SET SHOWPLAN_ALL ON.

    Utilidad: permite ver cómo procesa el motor la consulta por dentro y encontrar el cuello de botella: un table scan sobre una tabla grande, un sort costoso o muchas búsquedas por clave. Con eso se decide qué índices crear o modificar, cómo reescribir la consulta (por ejemplo, sacar una función aplicada a una columna, que impide usar su índice) y si las estadísticas están desactualizadas (filas estimadas muy distintas de las reales).

    Sirve también para comparar dos versiones de una consulta y quedarse con la de menor costo.

    Salió el 26/02/2020 y el 11/02/2025.

    Prácticos tipo A reales. Los resueltos completos de 2023 a 2025 están en Finales resueltos.

    1. Finales 2019 y 2025: PRODUCTOS tiene 15000 filas y DEPOSITO está vacía 
    SELECT p.prod_codigo, COUNT(*)
  FROM PRODUCTOS p, DEPOSITO d
 GROUP BY p.prod_codigo
HAVING COUNT(*) > 0
    d. 15000 × 0 = 0 filas. Sin filas no hay grupos, así que tampoco hay un COUNT = 0. El HAVING es una distracción.
    2. Finales 2022, 2024 y 2025: TABLITA(numero UNIQUE), más de 10 filas 
    SELECT MAX(t1.numero), MAX(t2.numero)
  FROM tablita t1, tablita t2
 WHERE t1.numero > t2.numero
    b. t1 puede ser cualquiera salvo el menor: su máximo es el mayor. t2 tiene que ser menor que algún t1: nunca puede ser el máximo, así que su máximo es el segundo. Solo hay agregados en el SELECT: no hace falta GROUP BY. Con MIN(t1) y MAX(t2) da el segundo menor y el segundo mayor (27/09/2023).
    3. Final 22/02/2023 (y 18/02/2025): TABLITAFINAL(numero UNIQUE) vacía, sin triggers 
    INSERT INTO tablitafinal VALUES (1);
INSERT INTO tablitafinal VALUES (3);
INSERT INTO tablitafinal VALUES (NULL);
UPDATE tablitafinal SET numero = ISNULL(numero, 5) + 1
 WHERE 1 = 1 OR numero IS NOT NULL AND numero > 0;
INSERT INTO tablitafinal VALUES (NULL);
COMMIT;
    c. AND antes que OR: el WHERE es siempre verdadero, el UPDATE toca las 3 filas: 1→2, 3→4, NULL→ISNULL(NULL,5)+1 = 6. Ya no queda ningún NULL, así que el nuevo INSERT NULL entra (UNIQUE admite uno). Cada sentencia se confirmó sola (autocommit): el COMMIT final da error porque no hay transacción abierta, pero no deshace nada.
    4. Final 05/03/2024: Numeros(numero PK) con N filas (N > 4). ¿Cuántas filas devuelve? 
    SELECT 1
  FROM Numeros t1, Numeros t2
 WHERE t1.numero < t2.numero
 GROUP BY t1.numero, t2.numero
    e. Una fila por cada par con el primero menor: N(N − 1)/2 = 1 + 2 + … + (N − 1). Como los números no se repiten, el GROUP BY no junta nada.
    5. Escribí la consulta: final 29/07/2025, los países que no tienen ciudades cargadas

    Modelo: Pais(idpais, detalle) → Provincia(idpcia, idpais, detalle, habitantes) → Ciudad(idciudad, idpcia, detalle).

    Ver una solución 
    SELECT p.idpais, p.detalle
  FROM Pais p
 WHERE NOT EXISTS (SELECT 1
                     FROM Provincia pr
                     JOIN Ciudad c ON c.idpcia = pr.idpcia
                    WHERE pr.idpais = p.idpais);

    Incluye a los países sin provincias y a los que tienen provincias sin ciudades. Con NOT IN también sale, pero NOT EXISTS no tiene el problema de los NULL.
