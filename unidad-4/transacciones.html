    Describa transaccionalidad, aislamiento y bloqueos la más tomada

    Una transacción es un conjunto de sentencias que el DBMS ejecuta como una unidad: se confirman todas (COMMIT) o se deshacen todas (ROLLBACK). Cumple ACID: atomicidad, consistencia, aislamiento y durabilidad.

    El aislamiento define qué ve una transacción de las demás que corren a la vez. Hay 4 niveles: READ UNCOMMITTED (permite lecturas sucias, no repetibles y fantasmas), READ COMMITTED (evita las sucias; es el default de SQL Server), REPEATABLE READ (evita también las no repetibles) y SERIALIZABLE (evita además los fantasmas).

    Para lograrlo, el motor usa bloqueos: compartidos para leer (compatibles entre sí), exclusivos para escribir y promovibles (de actualización), a nivel fila, página, tabla o base. Escribir siempre bloquea en exclusivo hasta el final; el nivel cambia los bloqueos de lectura: RU no los pide, RC los suelta al terminar de leer, RR los mantiene hasta el COMMIT y SERIALIZABLE bloquea además el rango leído.

    Más aislamiento: menos anomalías, pero más esperas y más deadlocks.

    Salió el 17/07/2018, en 2022, el 18/10/2024 y el 10/12/2024.

    ¿Qué representa la sigla ACID? 5 veces

    ACID son las cuatro propiedades que debe cumplir una transacción para que un DBMS se considere transaccional:

    • Atomicidad: se ejecuta completa o no se ejecuta; si algo falla, el ROLLBACK deshace todo (usando el log).
    • Consistencia: lleva la base de un estado válido a otro válido, sin violar las reglas de integridad (PK, FK, CHECK, triggers).
    • Aislamiento: las transacciones concurrentes no se interfieren; cada una ve los datos según su nivel de aislamiento, que el motor implementa con bloqueos.
    • Durabilidad: después del COMMIT, los cambios persisten aunque se caiga el sistema; el log permite recuperarlos (recovery).

    Ejemplo: una transferencia debita una cuenta y acredita otra; con ACID no puede quedar solo el débito.

    Salió el 12/03/2018, el 26/02/2019, en 2022, el 05/03/2024 y el 29/07/2025.

    Niveles de aislamiento y qué bloqueos usa cada uno 5 veces

    El nivel de aislamiento define cuánto se protege una transacción de las demás. Toda escritura toma bloqueo exclusivo hasta el fin de la transacción; los niveles difieren en el bloqueo de lectura:

    • READ UNCOMMITTED: no pide bloqueo compartido al leer, así que ve datos sin confirmar. Permite lectura sucia, no repetible y fantasma. Máxima concurrencia.
    • READ COMMITTED (default): bloqueo compartido solo mientras lee. Evita la lectura sucia; permite la no repetible y el fantasma.
    • REPEATABLE READ: mantiene el compartido sobre lo leído hasta el COMMIT. Evita sucia y no repetible; permite fantasmas, porque no bloquea los inserts.
    • SERIALIZABLE: además bloquea el rango leído, así nadie inserta filas que cumplan el WHERE. Evita las tres; menos concurrencia y más deadlocks.

    Sucia: leer lo no confirmado. No repetible: releer una fila y que haya cambiado. Fantasma: repetir una consulta y que aparezcan filas nuevas.

    Salió el 04/12/2019, el 09/09/2022, el 06/12/2022, el 23/07/2024 y el 11/02/2025.

    Un ejemplo para READ UNCOMMITTED y otro para SERIALIZABLE 2 veces

    READ UNCOMMITTED sirve cuando importa la velocidad y un dato aproximado no hace daño. Ejemplo: un tablero que muestra cada minuto los pedidos del día. Leer sin bloqueos no frena a las transacciones que cargan pedidos, y si cuenta uno que después se deshace, el error es despreciable.

    SERIALIZABLE sirve cuando un dato inconsistente es inaceptable. Ejemplo: vender el último asiento de un vuelo o generar números de factura sin huecos ni repetidos. Al bloquear el rango leído, dos transacciones no pueden ver «queda 1 asiento» a la vez: la segunda espera, o es víctima de un deadlock y se reintenta. Se paga con menos concurrencia.

    Salió el 25/07/2023 y el 12/12/2023.

    🟩 Ejercitá

    Cómo resolver un ejercicio de procesos en los tiempos T1…Tn

    1. Anotá el nivel de cada proceso. Si no lo dice, es READ COMMITTED. Ojo: el SET puede estar en un tiempo posterior al BEGIN.
    2. Recorré los tiempos y anotá qué bloqueo pide cada sentencia: SELECT pide S (salvo en READ UNCOMMITTED); INSERT, UPDATE y DELETE piden X hasta el final.
    3. ¿Cuánto dura cada S? En READ COMMITTED se suelta apenas termina el SELECT; en REPEATABLE READ y SERIALIZABLE, al COMMIT.
    4. Si un pedido choca con un bloqueo ajeno, ese proceso espera y no ejecuta sus tiempos siguientes. Si los dos se esperan entre sí: deadlock, uno es víctima (ROLLBACK).
    5. Leé el código letra por letra. Nombre de tabla o columna mal escrito, más valores que columnas, PK repetida, COMMIT sin BEGIN: la cátedra los usa para que la respuesta sea «ninguna».
    6. Al final, mirá qué quedó confirmado. Lo que hizo un proceso antes de su ROLLBACK no queda.

    Escribí el código: descontar stock sin que quede negativo

    En los finales del 28/02/2023 y 01/08/2023 este SP dejaba el stock en negativo con READ COMMITTED y daba deadlocks con niveles altos. Escribí una versión correcta en T-SQL.

    CREATE PROCEDURE descuenta_stock (@prod_id INT, @id_dep INT, @cant INT)
AS
BEGIN TRANSACTION
  IF EXISTS (SELECT 1 FROM stock
             WHERE id_producto = @prod_id AND id_deposito = @id_dep
               AND cantidad >= @cant)
  BEGIN
    UPDATE stock SET cantidad = cantidad - @cant
    WHERE id_producto = @prod_id AND id_deposito = @id_dep
    COMMIT
  END
  ELSE
    ROLLBACK
    Ver una solución

    La clave: validar y descontar en una sola sentencia. El UPDATE bloquea la fila antes de evaluar el WHERE, así que dos ejecuciones no pueden validar el mismo stock.

    -- Motor: SQL Server (T-SQL)
CREATE PROCEDURE descontar_stock
  @prod_id INT, @depo_id INT, @cant INT
AS
BEGIN
  SET NOCOUNT ON;
  BEGIN TRY
    BEGIN TRANSACTION;

    -- validar y descontar juntos: no queda un hueco entre leer y escribir
    UPDATE Stock
       SET cantidad = cantidad - @cant
     WHERE id_producto = @prod_id
       AND id_deposito = @depo_id
       AND cantidad >= @cant;

    IF @@ROWCOUNT = 0
      THROW 50001, 'No hay stock suficiente en ese depósito.', 1;

    COMMIT TRANSACTION;
  END TRY
  BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
    THROW;  -- devuelve el error original a quien llamó
  END CATCH
END;

-- red de seguridad: el motor rechaza cualquier stock negativo
ALTER TABLE Stock ADD CONSTRAINT ck_stock_no_negativo CHECK (cantidad >= 0);

    ¿Por qué no subir a REPEATABLE READ? Evita el negativo, pero los dos procesos retienen su S y piden X: cambiás un error por deadlocks.
